AIETargetModel.h BaseNPU2TargetModel returns rows() = 6 — "1 Shim row, 1 memtile row, and 4 Core rows" — with getTileType mapping row 0 to ShimNOC, row 1 to MemTile and rows 2–5 to CoreTile (which is exactly why whisper_fa uses row = 2 + ty). The kernel's own amdnpu.rst independently states "AMD Strix Point client APU have 4x8 topology" and "AMD Strix Point NPU has a total of 4096 KB of L2 memory" — 8 × 512 KB. An earlier revision of this page claimed 3 MB addressable per column. There is one memtile row, so per-column L2 is 512 KB. Corrected.

__AIE_API_FP32_SUPPORT__ = 0 in aie_api/aie2p/config.hpp. This is the single most important fact for an fp32 host op: moving a float32 op to the AIE costs you an emulation, not a native unit. bf16 8×8×8 costs two native 4×8×8 ops and two accumulators.

Whole-array bf16 peak ≈ 50 TOPS at 1.5 GHz nominal (1.76 GHz measured; 1.8 GHz max per AMD). Achieved: 37.35 TOPS int8 on the best published kernel.

Two constraints that bite kernel authors, both from BaseNPU2TargetModel: getComputeTileMaxVectorAlignBits() = 512, so a full-width vector access needs 512-bit alignment even though the load/store bus is 256-bit — a buffer that is merely 256-bit aligned will fault or silently split. And the array is virtualizable: VirtualizedNPU2TargetModel exists for TK_AIE2_NPU2_1Col through _7Col, so a design may claim 1–7 columns instead of all 8. A design that wants all 8 must say so, and cannot assume it.

This is the LayerNorm finding. LayerNorm needs rsqrt, and invsqrt is scalar-only — 83 emitted instructions for a 32-lane vector. A native LayerNorm design would be dominated by the reciprocal square root. Either pay it, or use a power-of-two seed plus Newton iterations on the vexp2/shift path. This is measurable and unclaimed work.

Movement and reduction paths

DDR

~50 GB/s effective for the NPU, measured. System LPDDR5x is 256 GB/s and shared with CPU and iGPU — so the NPU ceiling is ~20% of system bandwidth and is contended, not dedicated.

AIE cores cannot address DDR directly. The only path is shim DMA: shim NoC → SoC fabric → DDR.

Cascade flow

512 bit/cycle fixed, one accumulator beat per cycle. Direction is N/W → S/E; one in, one out; endpoints cardinally adjacent.

Shim and memtiles have no cascade interface — a cascade can never reach host memory. The last core must land the result in L1 for a normal ObjectFifo DMA. Caps a vertical chain at 4 cores/column, which is exactly what our FA_CASCADE_STAGES=4 uses.

Channel budget

Shim and compute tile: 2 MM2S + 2 S2MM each. Memtile: 6 + 6.

A 2-input kernel already consumes both shim MM2S channels of a column. A 3-input mapping cannot be fed from a compute tile. ObjectFifo depth rule: depth ≥ producer_outstanding + consumer_outstanding.

Buffer-descriptor limits (inherited from AIE2)

Address generation is 32-bit granular. A DMA can never perform a layout transform at sub-32-bit element granularity, so an int8 or bf16 swizzle must be done with in-core vshuffle. Locks: 64 per memtile, 16 per core/shim, 6-bit (max 63). Practical ObjectFifo guidance: ≈8 objects max in L1; deeper buffering goes to a memtile ObjectFifo with depth ≥ 4.

Two facts that shape any profiling work

One accel fd per pid. amdxdna_pci_drv.c:189-193 returns -EBUSY on a second open() by the same process. Any ioctl probe must live in a separate or forked process.

Runtime-parameterised kernels are an ELF-flow concept. xrt::ext::kernel exists, but get_ctrl_scratchpad_bo() throws "No module associated with run object" on our raw-instruction path. Our runtime parameters are baked into the xclbin, not patched at launch.

Attention qk / av THE REAL WORK

qk() (:3070) and av() (:3168) dispatch a qk_impl<8> on head_dim and have zero dispatch_only or sync_to_device anywhere in their bodies. There is no branch to enable.

Two routes, both already existing code:

(a) Reuse open_kernels/designs/whisper_fa/ — a flash-attention kernel ported from AMD's MLIR-AIR to IRON, hardware-verified byte-identical vs AIR on real Whisper layers, for an encoder. Laya's shape passes all seven of its asserts: FA_LQ=FA_LK=FA_VALID_LEN=1024, FA_LQP=256, FA_LKP=64, FA_DK=FA_DV=64, FA_NUM_HEADS=12, FA_HEADS_PER_UNROLL=2, FA_CASCADE_STAGES=4. The column budget is HEADS_PER_UNROLL × NQ = 2×4 = 8, exactly AIE2P's 8 columns — FA_NUM_HEADS is the loop count, not the width. Whisper's point is identical except those three constants. It removes the O(seq²) tensor entirely rather than relocating it.

(b) Upgrade ironvenv to current IRON and use operators/mha, which takes num_heads/seq_len/num_KV_heads and handles padding. This is the operator the original survey named.

Both need one number first: is the padding mask a prefix? valid_len is a prefix mask and Laya pads short states.

Not microarchitectural guesses — these are what amdnpu.rst states the driver and firmware do, and they bound what a host program may assume.

Concurrency and memory

propertyvalueconsequence
Concurrent workload contexts16 Strix Point; Phoenix/Hawk Point only 6. Not our limit — we use one.
Instruction buffer64 MB Host-resident, per context, PASID-protected, mapped into ERT and user space. Paid whether or not a design is large.
Partitioningcolumn granularity Spatial partitions are set up by the microcontroller programming column-isolation registers; each carries its own PASID.
Column allocationResource Solver The driver repartitions the array from workload-declared hints plus its own heuristics, and firmware enforces the binding. A design cannot assume it receives the columns it asked for.

Submission path, end to end

The host compiles an overlay (stream-switch configuration plus per-tile ELF) and a ctrlcode opcode stream. Userspace opens a context; the Resource Solver provisions columns; MERT creates an ERT and maps the 64 MB instruction buffer; userspace writes ctrlcode into it, submits a command buffer over the mailbox and sleeps. ERT executes ctrlcode, which kicks off DMAs to and from host DDR while the array runs, then raises MSI-X to wake the waiter.

DMA is encoded as XAIE_IO_BLOCKWRITE opcodes inside ctrlcode — which is why the XAIE_IO_* table matters when reading a captured instruction stream, and why a host-side dispatch call is not the same event as a data movement being issued.

Two traps, both measured

1. The column-utilisation protocol has no size query. amdxdna_query_sensors() with buffer_size == 0 returns rc 0 and zero bytes. utilities/npu-sensors.cpp uses exactly that two-call protocol, which is why it always reports 0 records. Pass a full 16-record buffer → 9 records return.

2. Utilisation needs ~4 s of warmup to reach a 98% peak, then decays over ~5 s. Measured 2026-10-02 during a real oflm run, sampling every 0.35 s: 2 → 31 → 52 → 66 → 83 → 92 → 98% at t≈5.6 s, then 81 → 56 → 40 → 28 → 14 → 5 → 1%. An earlier note here said "~8 s ramp to 100%"; that was inferred from a coarser sampling interval and the peak is 98%, not 100%. A 40-dispatch burst only reached 18%. Warmup is mandatory or every short run reads as idle — which is exactly how this instrument gets wrongly declared broken.

All 8 columns report the identical value: it is partition-wide, replicated per column, not 8 distinguishable signals.

The engagement proof that actually works

Not power. Corrupt the instruction stream.

pristine   cd0ad90a2f20d7724e6b6c23e30eaffb  → completes, logits printed
corrupted  0adf1b4e3005ecd595780752eee28d56  → REFUSED: gemm_rtp: kernel state 5

The device executed the corrupted instructions and reported a bad kernel state. No host fallback can produce a device kernel state, so this is direct proof of dispatch — strictly stronger than a timing or power signal, and it cannot be confounded by host work.

A power dose-response does not work here, and I shipped one that appeared to. Scaling the batch scales the host attention too, so a rising reading may be entirely host work. It would have passed with the encoder doing nothing on the NPU.

Recorded because a reader should not have to rediscover them, and because two of them were mine.

Wrong: NPU power is 1000× too high

I recorded a peak of "885 mW" and later read 1,041,000 as mW. power1_input is microwatts. amdxdna_sensors.c:144 computes *val = npu_power * MICROWATT_PER_MILLIWATT where npu_power is a u16 in milliwatts. The real figure was 0.89–1.05 W, and the field saturates at 65.5 W, so a reading of exactly 1,048,575 µW is a clipped field. I had written "read the sysfs attribute's units" into a skill and then did not.

Wrong: the dispatch counters are inert

drm-engine-amdxdna_accel_driver tracks NPU occupancy to within 0.8% over four runs, and column utilisation reaches 98%. Neither is broken. The zero readings came from sampling the wrong process: pgrep -f layaacc matched the bash wrapper, so 35 samples were taken of a shell whose only device fd was /dev/null.

The lesson was already in the skill I wrote that session — under a different heading. The failure was reading my own rules and not applying them.

Wrong, then over-corrected: the IRON operator library

I wrote a correction document asserting the operator list was fabricated because no operators/ directory exists. It exists upstream — cloned, with mha, rope, rms_norm, softmax, flm and the rest. The original survey was right about IRON and wrong about this box: the installed mlir_aie-1.4.2 predates the operator package. A version gap, not a fabrication. Two survey errors in one session, and the second was a correction of the first.

Wrong: the Q-scaling bug caused the 0.60 agreement

Written in the past tense, in a commit message and a skill, about a re-measurement that had not happened. Measured, both arms: 36/60 = 0.600 either way, residual 0.8434 → 0.6258. The fix is real; it moved agreement by nothing. The disagreements are near-ties, and the fixture has no decided pair (widest reference gap 0.0427 against a 0.20 threshold).

Right, and worth keeping: dispatch is proven. By corruption, not by power. And there is no host fallback — an empty design directory exits 1 in 0 s naming the design.json it could not find, so the only route to an answer is through the AIE.
